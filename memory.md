# Stable decisions

- Center is an ordinary signaling-server instance behind the load balancer, using the same signaling-server binary and listener as HTTP APIs, player hosting, and WSS. The dev deployment uses 8443; `-center` enables its admission/redirect routes. There is no standalone Center service/9443 listener.
- The canonical agent-created architecture/integration document is design/sid_licensing_architecture_v2.md; duplicate mobile, tenant, fleet, review, and camera SID notes were consolidated into it. Existing READMEs remain entrypoints.

- Camera viewing requires the activated camera publisher SID and its current shared password. Center receives only the SID and issues a 60-second player ticket scoped to the camera (`cid`); MainServer enforces that scope and supplies the trusted SID digest to the camera. No separate viewer SID or stored pairing grant is required.
- Pairing credential delivery, ownership, password-change authorization, and recovery are external. Password changes keep the SID unchanged. The camera consumes an atomic password-verifier replacement and closes existing viewers when the change is observed.
- Demo `player/ws.html` keeps the selected camera SID in a hidden field. The password input matches the former SID input styling; Play clears it immediately and sends only the captured attempt password after asynchronous ticket/WSS setup. Manual SID entry is absent. This UI change does not implement the proposed challenge-response protocol.

- SID v2 is 118 unpadded Base64URL characters (24-byte version/issue-time/flags/tenant/nonce payload plus 64-byte Ed25519 signature). Historical 107-character design text describes the earlier format.
- Local SID issuance helpers are `tools/sid_gen/gen_sid.sh COUNT [TENANT]` and `tools/sid_gen/list_sid.sh`, symlinked as `../sid_gen/gen_sid.sh` and `../sid_gen/list_sid.sh`. Generation defaults to tenant `test01` and role `publisher`; raw batch CSV/XLSX files are mode 0600 under `sid_gen/generated/`, while the manifest contains digests only. Listing joins those saved SIDs to digest-only audit history and marks audit-only legacy entries unavailable; it does not establish activation status.

- Recording control uses the current viewer data channel: type recording, actions list/play/stop, requestId, and relative path for play. Replies are list/playing/live/ended/error.
- RecordingController ignores stale connections and superseded media requests. Recordings switch only the requesting viewer; stop and EOF return to live.
- Camera display nicknames use authenticated WSS `{type: "register", nickname: ...}` metadata, capped at 128 UTF-8 bytes with control characters rejected. Nicknames are escaped display text; ticket-derived ID, tenant, role, and camera scope remain authoritative.
- `-discovery-tenant NAME` enables public, read-only `/api/devices` camera metadata for that admitted tenant only; requires ticket admission and never enables anonymous WSS or changes scoped routing. Keep enabled only on the development PM2 entry.
- Raw camera commands use the existing configurable cmdServer at 127.0.0.1:9191.
